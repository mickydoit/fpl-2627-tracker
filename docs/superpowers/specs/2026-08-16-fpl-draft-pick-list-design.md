# FPL Draft — snake draft pick list (v02.1)

**Status:** approved design, not yet implemented
**Date:** 16 August 2026
**Scope:** the pre-draft pick-list optimiser only. Post-draft tracking, waivers,
trades and H2H standings are explicitly out of scope and get their own design.

## Why this is a separate version, not a feature

FPL Draft is a different game from the main game, not a variant of it. Verified
against `draft.premierleague.com/api/bootstrap-static` on 16 Aug 2026:

| | Main game (v01) | Draft (v02) |
|---|---|---|
| Prices / budget | £100.0m, `now_cost` per player | **none at all** |
| Player exclusivity | anyone can own anyone | one owner per player per league |
| Club limit | max 3 per club | **no limit** |
| Captain | doubles a player's score | **`captains_disabled: true`** |
| Squad | 15, 2/5/5/3, 11 start | identical |
| Scoring | goals 10/6/5/4, CS 4/4/1/0, defcon 2 @ 10/12 | **identical** |
| Acquisitions | transfers, price changes | waivers and manager-to-manager trades |
| League | overall rank | head-to-head, 3/1/0, 8 entries by default |

The consequence: the **projection model ports unchanged**, and the **optimiser
does not port at all**. v01's optimiser solves a budget-constrained knapsack.
With no budget and no club cap, that entire machine is irrelevant. Draft
selection is a scarcity problem — who is worth most *relative to whoever else
you could have at that position later*.

## Architecture

One projection engine, two adapters. v02 does not fork `js/model.js`.

v02 owns the cyan accent (`data-accent="cyan"` on `<body>`); v01 keeps lime.
The design system, tokens and generated-HTML rule from v01 all apply unchanged
— `draft.html` is generated by `scripts/build-pages.mjs` and must not be
hand-edited.

```
js/model.js            shared, unchanged except one injectable prior
js/draft/adapt.js      Draft bootstrap -> the row shape model.js expects
js/draft/board.js      replacement level, VORP, tiers
js/draft/simulate.js   snake order, opponent model, survival probability
js/draft/advise.js     the pick recommendation rule
js/pages/draft.js      big board, your picks, live mode
draft.html             generated by scripts/build-pages.mjs
data/draft/            committed snapshots
scripts/fetch-draft.mjs  the Action's Draft fetch step
```

### Data sources

- **`draft.premierleague.com/api/bootstrap-static`** — players, teams, element
  types, scoring settings, squad rules. Public, no auth. 587 players.
- **`fantasy.premierleague.com/api/fixtures`** — the season schedule and
  difficulty ratings. Required because Draft's own `fixtures` key holds only
  gameweeks 1–3 and its fixture objects carry no `team_h_difficulty` /
  `team_a_difficulty`. We already fetch this for v01; v02 reuses the snapshot.

Both are fetched server-side by the existing Action and committed as JSON, for
the same CORS reason that shapes v01.

### The adapter

Draft supplies season totals but no per-90 fields. All of them are derivable
from `minutes`:

```
xg90  = expected_goals / minutes * 90
xa90  = expected_assists / minutes * 90
xgc90 = expected_goals_conceded / minutes * 90
```

`saves_per_90` and `defensive_contribution_per_90` derive the same way from
`saves` and `defensive_contribution`. Players with zero minutes get no per-90s
and fall through to the prior, exactly as in v01.

The one genuinely missing input is `now_cost`, which `pricePrior()` depends on.
Draft has no prices, so the prior is rebuilt from `draft_rank` — the game's own
ordering of every player. `draftPrior(p)` maps rank to expected points per
appearance with a decaying curve fitted so that rank 1 lands near the top of
v01's price-prior range for the position and the curve flattens by roughly rank
200, then takes the higher of that and `points_per_game` where the latter
exists. Concretely, per position, the same clamp bounds as `pricePrior` apply,
so the two priors are interchangeable at the call site.

**Required change to shared code:** `pricePrior` is currently called directly
inside `projectFixture`. It becomes injectable via `opts.prior`, defaulting to
the existing price prior so v01 behaviour is bit-identical. This is the only
edit to shared code in this version.

## The model, applied to a draft

### Full-season horizon

v01 projects over a rolling 5-gameweek horizon because transfers make it a
short-term game. Draft value is season-long: you keep who you draft unless you
actively trade or waiver. v02 therefore projects across all remaining
gameweeks.

One consequence, stated because it changes the advice: **fixture difficulty
largely averages out over 38 gameweeks**, so FDR contributes far less than it
does in v01, and **minutes and role dominate**. A nailed-on starter beats a
rotation risk with better underlying numbers by a wider margin here than in the
main game. The projection still applies FDR per fixture; it simply matters less
once summed.

### Value over replacement

Ranking by raw projection is wrong in a draft. A keeper projecting 150 is worth
nothing if the 17th keeper projects 145; a defender projecting 150 is enormous
if the 41st defender projects 90. What matters is the gap to the player you
could still get at that position after the position has been picked over.

With `N` managers and squad quotas 2/5/5/3, the league drafts exactly `N×2`
keepers, `N×5` defenders, `N×5` midfielders and `N×3` forwards. Replacement
level at each position is the projected points of the next player after those:

```
replacement(pos) = projection of the (N * quota[pos] + 1)-th best player at pos
VORP(player)     = projection(player) - replacement(player.position)
```

**This league has 6 managers** (confirmed 16 Aug 2026), so replacement level is
GKP #13, DEF #31, MID #31, FWD #19. The board defaults to 6; league size stays
an input so the tool is not hardwired to one league.

### What six managers does to the problem

Six managers draft 90 of 587 players, leaving **497 in the free-agent pool**.
That is a shallow draft, and it changes the advice in three ways:

1. **Forwards are the scarce resource, and nothing else is close.** Measuring
   the gap from the best player to replacement level at each position (using
   2025/26 totals as a shape proxy): FWD 163, MID 110, DEF 94, GKP 57. Only 18
   forwards are drafted and the curve behind them collapses; 30 midfielders and
   30 defenders come off a much flatter curve. A board ranked on raw projection
   would miss this entirely — it is exactly what VORP exists to surface.
2. **Never draft a keeper early.** GKP #13 is still available as a free agent,
   and the whole positional edge is worth 57 points across a season.
3. **Mistakes are cheap.** With 497 players unowned, a bad pick is recoverable
   on waivers. This argues against reaching, and against over-weighting the
   survival simulation: the snake gaps are short (a maximum nine-pick wait, and
   slots 5 and 6 pick almost back-to-back at the turn), so positional-run
   pressure is far weaker than in a 10- or 12-manager league.

Consequence for scope: the survival simulation stays in the design because it
still informs the first three rounds, where the elite tier does run out. But it
is explicitly the *secondary* signal here, and if it proves expensive to
calibrate it should be cut before VORP or tiers are compromised.

### Tiers

Tiers are the cliffs in VORP within a position — the points at which the next
player is materially worse. They are computed by scanning the sorted VORP list
for gaps larger than a threshold expressed in standard deviations of the
within-position gap distribution, starting at 1.0 sd and exposed as a tunable. Tiers tell you when a run is about to end,
which is the information VORP alone does not carry.

### Survival probability

The snake gap is the whole problem. In this 6-manager league the pick sequences by slot are:

```
slot 1:  1, 12, 13, 24, 25, 36, 37, 48, 49, 60, 61, 72, 73, 84, 85
slot 2:  2, 11, 14, 23, 26, 35, 38, 47, 50, 59, 62, 71, 74, 83, 86
slot 3:  3, 10, 15, 22, 27, 34, 39, 46, 51, 58, 63, 70, 75, 82, 87
slot 4:  4,  9, 16, 21, 28, 33, 40, 45, 52, 57, 64, 69, 76, 81, 88
slot 5:  5,  8, 17, 20, 29, 32, 41, 44, 53, 56, 65, 68, 77, 80, 89
slot 6:  6,  7, 18, 19, 30, 31, 42, 43, 54, 55, 66, 67, 78, 79, 90
```

Slot 1 waits longest between picks (1 to 12); slots 5 and 6 pick nearly
back-to-back at each turn and so face the least uncertainty.

Snake order, 1-indexed round `r` and slot `s` in a league of `N`:

```
odd  round: pick = (r - 1) * N + s
even round: pick = r * N - s + 1
```

Opponents are modelled as picking from the top of the remaining board by
`draft_rank`, softened with noise, and respecting their own positional quotas
(a manager holding two keepers cannot draft a third). Running `M` simulated
drafts with a fixed seed gives, for every player, the probability they survive
to each of your picks. Fixed seed matters for the same reason it does in v01: a
board that reshuffles on reload is impossible to act on.

### The recommendation rule

At each of your turns, recommend the player maximising:

```
VORP(p) - E[ best VORP available at your next pick, if you pass on p ]
```

That is the positional-run logic in one line. It recommends the player who will
not come back to you, rather than simply the highest-rated one available, and
it naturally declines to draft a keeper early because keepers survive.

## Outputs

Three views on one page, sharing state:

1. **Big board** — every player ranked by VORP, with position, tier, projection,
   `draft_rank` for comparison, and survival probability at your next pick.
2. **Your picks** — each of your slots pre-computed, with a primary target and
   two fallbacks, and the expected board state when your turn arrives.
3. **Live mode — the primary deliverable.** The board, tiers, replacement
   levels and survival odds recompute as picks land. Everything else exists to
   support this view.

The draft slot is **not** a required input. It is derived: the manager picks
their own name once from the league's entry list, and the slot falls out of the
first round of picks.

### Reading the live draft

Two endpoints are public and need no authentication (verified 16 Aug 2026):

- `GET /api/league/{league_id}/details` — `league_entries` (every manager),
  scoring type, `draft_dt`, and `draft_pick_time_limit` (60 seconds).
- `GET /api/draft/{league_id}/choices` — `choices` as picks land, and
  `element_status`: all 587 players with an `owner` field.

The Draft API sends no `Access-Control-Allow-Origin`, so the browser cannot
call it — the same constraint that shapes v01. The scheduled Action is also
useless here: it runs every 30 minutes against a 60-second pick clock.

**Resolution: a local poller.** `npm run draft-live` runs a node script on the
manager's own machine during the draft, polling `choices` every 5 seconds and
writing `data/draft/live.json`, which the page reads same-origin. Node is not a
browser, so CORS does not apply. The poller stops when `draft_status` leaves
`live`. Polling is roughly 90 picks over an hour or two at 5-second intervals —
modest, and well within the pick clock.

**Fallback: manual entry.** If the manager is away from the laptop, players can
be marked taken by hand. The board must work identically either way, so live
state is modelled as a single `owner`-by-element map regardless of source.

### What live state does to the simulation

With the board state known exactly, we never simulate a whole draft. Only the
opponent picks between the manager's current turn and their next need
predicting — at most five in this league. That makes the simulation both
cheaper and materially more accurate than the full-draft model originally
specified, and it removes most of the calibration risk flagged below.

League size and draft slot are inputs, defaulting to this league's 6 managers, so the board is usable before the
slot is known.

## Testing

All the new logic is pure and testable without a DOM, and goes in the existing
`scripts/test.mjs` suite:

- snake pick order for a range of league sizes and slots, including both edges
  (slot 1 and slot N) where the double-pick turnaround happens
- replacement level: correct rank per position for several league sizes
- VORP: ordering, and that it demotes keepers relative to raw projection
- tier boundaries fall at genuine gaps, and tier count stays sane
- simulation determinism: same seed, same survival numbers
- survival monotonicity: a player's survival probability never rises at a later
  pick
- the adapter: per-90 derivation matches hand-computed values, zero-minute
  players fall to the prior
- **baselines**: our board is scored against `draft_rank` order and against
  plain best-available, on simulated drafts. If we do not beat both, the
  approach is not working and the test says so.

Live mode is verified in a real browser, as the drag-and-drop work was.

## Out of scope

Deliberately excluded from v02.1, each needing its own design pass once a real
squad exists:

- post-draft points, fixtures and stats tracking
- waiver and free-agent suggestions
- manager-to-manager trade suggestions and valuation
- head-to-head league standings and projections

## Risks

1. **Stats are 2025/26 until the GW1 deadline (21 Aug).** Every per-90 the model
   derives is last season's. This affects v02 exactly as it affects v01, and it
   matters more here because a draft is a one-shot decision. If the draft
   happens before the deadline, the board is built on last season's form and
   should be read with that in mind.
2. **The opponent model is a guess.** Real managers draft on reputation, news
   and their own hunches. `draft_rank` plus noise is a reasonable proxy but it
   is not calibrated against real drafts, and survival probabilities inherit
   that uncertainty. They are directional, not precise.
3. **The bonus component is still calibrated on the old BPS.** Same known gap as
   v01, and it propagates here.
